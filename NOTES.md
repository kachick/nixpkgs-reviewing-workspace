# Development Notes

## Security Boundaries & Threat Model

### Build-time Sandboxing vs Run-time / Test Execution

- **Build-time isolation in Nix**:
  - In standard Linux environments, Nix builds packages inside isolated user and mount namespaces with network access disabled by default.
  - As long as builds run within this sandbox, running untrusted build expressions is generally safe from host mutation or secret exfiltration.
- **Darwin (macOS) sandbox limitations**:
  - macOS sandboxing relies on Apple's seatbelt framework, which has known limitations compared to Linux namespaces.
  - Past vulnerabilities (such as [GHSA-qc7j-jgf3-qmhg](https://github.com/NixOS/nix/security/advisories/GHSA-qc7j-jgf3-qmhg)) demonstrate derivation sandbox bypass risks on Darwin.
  - Furthermore, many macOS builds require `sandbox = false` (or relaxed sandboxing) due to toolchain and code signing requirements, significantly weakening isolation.
- **Package execution and test risks (`--tests`)**:
  - Executing built packages or running package tests (such as `passthru.tests`) does not share the same strict build-time sandbox guarantees.
  - If a reviewed package or its test suite contains malicious code, executing tests can directly access runner environment variables (such as tokens) or interact with the host system.
  - Therefore, running package tests on untrusted pull requests requires extra caution and should remain an explicit opt-in choice.

### Secret Exposure in Reports and Artifacts

- **GitHub Actions log masking boundary**:
  - GitHub Actions masks registered secrets in console logs, but does NOT mask them in downloaded workflow artifacts (`upload-artifact`) or workflow summaries (`GITHUB_STEP_SUMMARY`).
  - Anyone with read access can download workflow artifacts.
  - Summaries generated by `resume` are frequently copied and pasted into public GitHub issues and PR comments.
- **Fail-safe leak scanning with `betterleaks`**:
  - If a malicious or buggy package dumps environment variables during a build failure or test run, those secrets could leak into `report.md` or build log files.
  - To prevent leaks:
    1. Scan review artifacts with `betterleaks` before uploading.
    2. Scan combined reports in `resume` with `betterleaks` before printing to summary or stdout.
    3. Fail the job if any potential secret leak is detected (fail-safe).

### Binary Cache Management & Token Isolation

- **Step isolation for Cachix authentication**:
  - `CACHIX_AUTH_TOKEN` is passed only to the push step after `nixpkgs-review` finishes.
  - The review execution step runs without `CACHIX_AUTH_TOKEN` in its environment to reduce secret exposure risks during evaluation, building, and tests.
- **Cache pin naming and retention**:
  - Pin names use `review-nixpkgs-<pr-number>` (or `review-nixpkgs-<args-hash>` for custom args).
  - Built packages are grouped into a `linkFarm` derivation and pinned with `--keep-days 21`.
- **Upload size threshold**:
  - Pushes larger than 2 GiB in total package size are skipped with an Actions warning to avoid wasting cache storage.
- **Target runner and opt-out**:
  - Pushes run only on `x86_64-linux` runners and can be disabled with the `push-cache` workflow input.
- **Excluding downstream rebuilds**:
  - Only root review targets are uploaded and pinned to Cachix. Downstream packages rebuilt as side-effects are filtered out by inspecting Nix package requisites.
